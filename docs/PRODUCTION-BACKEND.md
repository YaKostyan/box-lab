# Production backend contract

Поточна GitHub Pages-версія залишається автономним прототипом і використовує `localStorage`. Щоб не вигадувати реквізити, SMS-провайдера або інфраструктуру власника, реальний API підключається окремо після вибору хостингу.

## Мінімальні сутності

- `products`: номер, назва, внутрішні розміри, базова ціна, видимість, час оновлення;
- `accounts`: телефон, ім’я, компанія, роль, статус постійного клієнта;
- `orders`: клієнт, контактні дані, позиції, зафіксовані ціни, сума, статус, нотатка менеджера;
- `sessions`: серверна сесія з терміном дії та відкликанням;
- `audit_log`: хто і коли змінював товар, клієнта або замовлення.

## Мінімальні маршрути

| Метод | Маршрут | Доступ |
|---|---|---|
| `POST` | `/auth/request-code` | публічний, з rate limit |
| `POST` | `/auth/verify-code` | публічний |
| `POST` | `/auth/logout` | авторизований |
| `GET` | `/products` | публічний |
| `POST` | `/orders` | публічний або клієнт |
| `GET` | `/me/orders` | клієнт |
| `GET/POST/PATCH` | `/admin/products` | менеджер |
| `GET/PATCH` | `/admin/orders` | менеджер |
| `GET/PATCH` | `/admin/clients` | менеджер |

## Обов’язкові правила

- ціна повторно розраховується на сервері, а не приймається з браузера;
- пароль не зберігається у відкритому вигляді; для входу за телефоном бажано використати одноразовий код;
- роль менеджера перевіряється сервером на кожному admin-маршруті;
- дані перевіряються й очищуються на сервері;
- зміна ціни або товару записується в `audit_log`;
- видалення товару робиться м’яким, якщо він уже присутній у замовленнях;
- заявка створюється транзакційно разом із її позиціями;
- після створення заявки сервер надсилає менеджеру повідомлення обраним власником каналом;
- резервні копії та політика зберігання даних визначаються до приймання реальних заявок.

## Що не можна зберігати у фронтенді

- паролі, SMS-секрети та service-role ключі;
- право доступу до адмінки;
- довірену кінцеву ціну;
- приватні нотатки менеджера.
